# PrincipleGraph 项目上下文

## 项目愿景

PrincipleGraph 面向 Java 开发工程师，将面试中零散的技术知识组织为可逐层下钻、可双向引用、可沿执行方向阅读的交互式原理图谱。

用户从一个完整业务场景进入，例如“一次 HTTP 请求在多实例微服务系统中的全过程”，点击图中的服务器、容器、Java 服务、数据库或 JVM 等节点，逐层进入更细的原理链路；每一层都必须同时提供：

- 一条或多条方向明确、起点和终点完整的执行链路；
- 与图中节点对应的文字解释；
- 返回上层、面包屑和历史路径；
- 指向相关知识页的双向引用；
- 后续扩展具体项目和业务场景的稳定数据结构。

## 首要用户

1. 准备 Java 面试、需要建立知识体系的工程师；
2. 希望从业务请求反推底层原理的在职开发者；
3. 负责整理、审查和发布知识内容的维护者。

## MVP 边界

MVP 只验证“结构化学习体验”，不追求知识总量。首条内容主干为：

`客户端 HTTP 请求 -> DNS/CDN/LB/Gateway -> 多实例服务 -> Linux/Docker -> Spring Web -> 业务事务/缓存/MySQL -> JVM 线程执行`

最低内容规模：

- 8 个可独立访问的知识页；
- 60 个以上节点、70 条以上流程边；
- 12 条以上跨页双向引用；
- 每页至少一条可从入口走到出口的完整主链路；
- 至少 4 层连续下钻路径。

## MVP 产品假设

- 首版主要是公开只读浏览，内容由仓库内 YAML/JSON 文件维护并经 Git 审查后导入；
- 首版不实现多人实时协同和自由手绘；
- 层级关系使用“下钻链接”表达，要求无自环且默认不形成环；相关性关系允许成环；
- 一页只展示当前层级的有限节点，避免把全量知识图谱一次性渲染；
- 中文搜索首版覆盖标题、别名、标签和说明摘要，不承诺语义搜索。

## 待验证问题

1. 用户更常从“业务场景”还是从“知识点搜索”进入；
2. 单页 8–20 个节点是否最利于理解；
3. 用户能否仅凭视觉语义区分流程边、下钻链接与相关引用；
4. 文字解释应固定在右侧面板，还是作为画布中的注释块；
5. 首批内容应更偏面试高频，还是更偏生产请求链路。

## 成功信号

- 新用户在 3 分钟内完成一次至少 3 层的有效下钻；
- 任务测试中 80% 以上用户能正确复述请求主链路；
- 搜索零结果率低于 15%；
- 发布内容不存在断裂下钻链接、悬空流程边或重复稳定键；
- 常规页面在目标设备上 2 秒内可交互，图谱切层 P95 低于 800ms。
